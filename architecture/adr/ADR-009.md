# ADR-009: Role-Based Access Control (RBAC)

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use RBAC with five system roles (Super Admin, Org Admin, Manager, Employee, Viewer) as the authorization model.

**Context:** Calyx is multi-tenant with multiple user roles per organization. We need an authorization model that is simple to understand, predictable, and enforceable at the database level.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **ACL (Access Control Lists)** | Per-object permission lists. Correct but operationally complex — every resource needs its own permission set. Management burden scales with resource count. |
| **ABAC (Attribute-Based Access Control)** | Policy-based, highly flexible. Rejected for MVP because policies are hard to reason about, hard to audit, and hard to debug. Overkill for five well-defined roles. |
| **ReBAC (Relationship-Based Access Control)** | Authorization based on entity relationships (à la Google Zanzibar). Powerful, but requires a dedicated authorization service. Premature for MVP. |

**Why RBAC:**
- Simple mental model — "what role do I have? what can that role do?" Every user and admin can understand this.
- Predictable — given a role and a resource, the answer to "can I do this?" is deterministic.
- Auditable — permission checks are explicit function calls that can be logged and reviewed.
- Database-friendly — roles and permissions are tables with simple joins. RLS policies reference the user's role.
- Covers MVP use cases — five roles with a defined permission matrix handle all MVP authorization needs.

**Trade-offs:**
- Role explosion — if many fine-grained permission combinations are needed, the number of roles grows. Mitigated by contextual permissions (ADR-010) and future custom roles.
- Coarse granularity — RBAC answers "can this role do this action?" but not "can this role do this action *on this specific resource*?" Addressed by contextual permissions.

**Future Migration Path:** The schema stores roles and permissions as database records, not code enums. Custom roles (post-MVP) are additive. If ABAC is needed for enterprise customers, the `role_permissions` table can be extended with a `conditions` JSONB column for attribute-based constraints — no schema redesign required.
