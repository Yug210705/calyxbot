# ADR-020: Domain Events

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-07-01
**Owner:** Architecture Team

---

**Decision:** We will publish Domain Events (e.g., `OrganizationCreated`, `InvitationSent`, `RoleChanged`) immediately following successful domain mutations.

**Context:** The application needs a robust way to trigger side-effects (like sending emails or syncing analytics) without entangling the primary transaction boundary or slowing down the HTTP response. A Domain Event model allows decoupled handlers to react to core business actions asynchronously.

**Implementation Details:**
- Events are explicitly modeled (e.g., `dataclasses` or `Pydantic` models).
- We will start with a simple in-process event bus (e.g., FastAPI background tasks or a basic pub/sub mechanism).
- Mutation services publish these events to the bus rather than calling side-effect functions directly.

**Why:**
- Enforces single responsibility by isolating side-effects from core business logic.
- Makes unit testing easier (assert event published vs mocking an email service).
- Prepares the application for an eventual move to a distributed event broker (Kafka, NATS, or RabbitMQ).

**Future Considerations:** As scale increases, the in-process event bus will be replaced with a distributed message broker (e.g., Kafka) to ensure event durability and allow separate microservices or workers to consume them.
