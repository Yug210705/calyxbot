# ADR-005: Modular Monolith over Microservices

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Build Calyx as a modular monolith — a single deployable unit with clear internal module boundaries.

**Context:** We are a small team building an MVP. We need to move fast, iterate quickly, and avoid operational overhead. At the same time, we need an architecture that can evolve without becoming a tangled mess.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Microservices** | Premature for a team of our size. Adds distributed systems complexity (service discovery, inter-service communication, distributed transactions, deployment orchestration) without benefit until we have scale or team-size reasons to decompose. |
| **Serverless functions** | Cold starts hurt latency. Stateless execution makes background processing complex. Vendor lock-in to specific cloud platforms. Debugging is harder. |
| **Unstructured monolith** | Fast to start, impossible to maintain. Leads to spaghetti code and no clear module boundaries. |

**Why Modular Monolith:**
- Single deployment — one build, one deploy, one set of logs. Minimal operational overhead.
- In-process communication — modules call each other via function calls, not HTTP. No serialization overhead, no network failures.
- Shared database — no distributed transactions, no eventual consistency headaches.
- Clear boundaries — modules communicate through service interfaces, not direct repository access. This means extraction into separate services is possible later.
- Fast iteration — change, test, and deploy in minutes, not hours.

**Trade-offs:**
- Scaling is all-or-nothing. If one module is CPU-intensive, we scale the entire process. Acceptable at MVP scale.
- A bug in one module can crash the entire process. Mitigated by exception isolation and health checks.
- Module boundary discipline requires code review vigilance. No compiler enforcement.

**Future Migration Path:** When scale or team size justifies decomposition:
1. Identify the module with the strongest reason to be independent (likely the knowledge extraction/embedding pipeline).
2. Extract it behind a task queue — the monolith enqueues work, the extracted service processes it.
3. Repeat for other modules as justified.

The service interface boundaries are designed to make this extraction straightforward.
