# ADR-037: Multi-tenant Isolation Strategy

**Date**: 2026-07-02
**Status**: Accepted
**Domain**: Platform

## Context
As a multi-tenant SaaS, Calyx stores data for many organizations in a shared infrastructure. We must ensure absolute isolation so that Organization A cannot access Organization B's data, either accidentally or maliciously.

## Decision
We will enforce multi-tenant isolation at three layers:
1. **Application Layer (FastAPI)**: Every incoming request must be associated with an `organization_id` via `Request.state`. The `MembershipService` verifies the user's role in this exact organization before reaching business logic.
2. **Database Layer (PostgreSQL)**: All tables (except identity tables) strictly enforce a foreign key to `organization_id`. Repositories will implement a mandatory `org_id` filter on every query. Future scaling will evaluate Row-Level Security (RLS) if Supabase is maintained.
3. **Storage & Search Layer (pgvector/Graph)**: Vector indexes and Graph namespaces will be partitioned by `organization_id`. No cross-tenant graph traversals or vector searches are permitted. The `EmbeddingStore.batch_search` and `GraphStore` must accept `organization_id` as a mandatory parameter.
