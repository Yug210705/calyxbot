# ADR-002: Next.js as the Frontend Framework

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use Next.js (App Router) with TypeScript and Tailwind CSS.

**Context:** Calyx's frontend is a complex, multi-page application with authenticated routes, organization-scoped views, real-time-ish dashboards, rich text editing, and search interfaces. We need server-side rendering for SEO on public pages, client-side interactivity for the application shell, and a mature routing system.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Remix** | Strong data loading model, but smaller ecosystem and fewer enterprise deployments. Fewer UI component libraries. |
| **SvelteKit** | Excellent DX and performance, but smaller talent pool and component ecosystem. Riskier bet for an enterprise product. |
| **Vite + React SPA** | No SSR, no built-in routing conventions. We'd need to add routing, layout management, and middleware manually. |

**Why Next.js:**
- App Router provides file-based routing, nested layouts, and route groups — maps cleanly to our auth/platform/onboarding layout separation
- Server Components reduce client bundle size for data-heavy pages (dashboard, audit logs)
- Server Actions provide a secure, server-side environment for authentication flows (Supabase OAuth/password logins) and synchronizing state with the FastAPI backend without exposing internal network requests to the client.
- Middleware enables auth checks at the edge before page rendering
- Vercel deployment is zero-config, and the framework is optimized for it
- Largest React ecosystem — shadcn/ui, TanStack Query, and every major component library works out of the box

**Trade-offs:**
- Vercel coupling — Next.js works best on Vercel. Self-hosting is possible but less optimized. Acceptable for MVP.
- App Router complexity — Server Components, Client Components, Server Actions, and their interaction boundaries add cognitive overhead.
- E2E Testing Complexity — Since Server Actions run on the Node.js server, browser-based interceptors in Playwright cannot capture backend API requests. This requires using Playwright's native API Request context instead of `page.waitForResponse()`.
- Build times grow with app size. Not a concern at MVP scale.

**Future Migration Path:** Next.js is stable and widely adopted. No migration anticipated. If Vercel pricing becomes prohibitive, Next.js can be deployed on any Node.js hosting via `next start` or containerized.
