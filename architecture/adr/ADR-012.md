# ADR-012: Organization-First Multi-Tenancy with Shared Schema and RLS

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use a shared-schema, shared-database architecture with `org_id` on every tenant-scoped table and PostgreSQL Row-Level Security (RLS) for isolation.

**Context:** Calyx is multi-tenant. Every piece of data belongs to an organization. We need strong tenant isolation with minimal operational overhead.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Database per tenant** | Strongest isolation, but creates connection pool explosion, migration complexity, and operational cost that scales linearly with tenant count. |
| **Schema per tenant** | Good isolation, but Supabase doesn't natively support dynamic schema creation. Migration complexity scales linearly. |
| **Application-level filtering only** (no RLS) | Single point of failure. One missed `WHERE org_id = ?` clause leaks data. |

**Why Shared Schema + RLS:**
- Single migration path — one schema, applied once.
- RLS as defense in depth — even if the application has a bug, the database enforces isolation. Three-layer enforcement (API middleware → service layer → RLS).
- Supabase-native — RLS is a first-class Supabase feature with tooling support.
- Scales to thousands of tenants — PostgreSQL handles millions of rows across tenants efficiently with proper indexing.
- Simple operations — one database to backup, monitor, and maintain.

**Trade-offs:**
- Noisy neighbor risk — a tenant with heavy queries can affect other tenants' performance. Mitigated by connection pooling (PgBouncer, built into Supabase) and query timeouts.
- RLS policy complexity — complex policies are hard to write and debug. Mitigated by keeping policies simple (always filter by `org_id` from JWT claims) and testing them explicitly.
- No per-tenant resource limits at the database level. Rate limiting is the application layer's responsibility.

**Future Migration Path:** If a large enterprise customer requires dedicated infrastructure, they can be migrated to a dedicated Supabase project (database-per-tenant for that one customer) while all other tenants remain on the shared instance. The application layer routes by org to the appropriate database connection.
