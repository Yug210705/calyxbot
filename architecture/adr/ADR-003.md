# ADR-003: Supabase as the Backend Platform

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use Supabase for PostgreSQL hosting, authentication, and file storage.

**Context:** We need a managed PostgreSQL database with pgvector support, an authentication system with email/password and OAuth, and file storage for avatars and attachments. Building and operating these from scratch is undifferentiated work for a startup.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Firebase** | NoSQL (Firestore) is a poor fit for relational data with complex joins. Firebase Auth is good but locks us into Google's ecosystem. No pgvector equivalent. |
| **Auth0 + raw PostgreSQL + S3** | Best-of-breed per component, but three vendors to manage, three billing relationships, and more integration glue. Auth0 pricing escalates rapidly. |
| **Self-managed PostgreSQL + custom auth** | Maximum control, but massive operational burden. Auth is security-critical code we shouldn't write ourselves at this stage. |

**Why Supabase:**
- Managed PostgreSQL with pgvector extension — our primary data store and vector search in one database
- Built-in Auth with JWT, OAuth, email verification, and password reset — battle-tested, not hand-rolled
- Row-Level Security (RLS) — database-enforced tenant isolation, a critical security layer
- Storage with access policies — tenant-scoped file storage without managing S3 buckets
- Generous free tier for development, predictable pricing for production
- Open-source core — reduces vendor lock-in compared to fully proprietary platforms

**Trade-offs:**
- Vendor dependency — if Supabase has an outage, we have an outage. Mitigated by the fact that Supabase is built on standard PostgreSQL — we can migrate to any managed PostgreSQL provider (RDS, Cloud SQL, Neon).
- Auth customization limits — Supabase Auth handles standard flows well, but exotic auth requirements (e.g., device-bound tokens, step-up authentication) may require workarounds.
- RLS policy complexity — complex policies are hard to debug. Mitigated by defense-in-depth (service layer also enforces isolation).

**Future Migration Path:** Supabase is PostgreSQL. The database can be migrated to any PostgreSQL provider by exporting and restoring. Auth can be replaced with Auth0/Clerk/custom — our service layer abstracts auth behind its own interface. Storage can be replaced with S3-compatible services.
