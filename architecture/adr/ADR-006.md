# ADR-006: Source-Agnostic Memory Model

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** All knowledge sources (documents, Slack, GitHub, Jira, meetings, email) produce the same internal representation: a Memory unit.

**Context:** Calyx will ingest knowledge from many sources. We could either model each source type separately (with source-specific tables and schemas) or normalize everything into a single canonical representation.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Source-specific models** (separate tables for slack_memories, github_memories, etc.) | Fragments search, fragments the graph, creates N-way maintenance burden. Every new source requires new tables, queries, and UI components. |
| **Generic document store** (store raw source content, search over raw text) | Loses structure. A Slack thread and an architecture doc are fundamentally different — searching raw text across both produces poor results. |

**Why Source-Agnostic Memory:**
- Unified search — one table, one vector index, one ranking algorithm regardless of origin.
- Connected graph — all memories participate in the same graph. A Slack-sourced decision and a Google Doc-sourced specification can be connected directly.
- Integration simplicity — adding a new source requires only a new adapter and extractor. The memory layer, search, graph, confidence engine, and UI don't change.
- Provenance preserved — the source type and source reference are stored on every memory. We know where it came from without needing separate tables.

**Trade-offs:**
- Information loss — normalizing a rich Slack thread or a detailed PR review into a memory discards source-specific structure. Mitigated by storing `source_ref` (a link back to the original) and `metadata` (a JSONB field for source-specific attributes).
- Extraction quality varies — extracting a memory from a well-structured document is easier than from a rambling Slack conversation. Extraction quality is a pipeline concern, not a model concern.

**Future Migration Path:** No migration anticipated. The model is additive — new source types are new enum values and new adapter implementations. The memory schema is stable.
