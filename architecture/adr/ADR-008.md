# ADR-008: REST over GraphQL

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use REST (JSON over HTTP) for the API.

**Context:** The Calyx API serves the Next.js frontend and will serve future AI agents and third-party integrations. We need a stable, well-understood API paradigm.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **GraphQL** | Flexible queries, reduces over-fetching. Rejected because: (1) adds a query language layer the team must learn and maintain, (2) caching is harder (no HTTP-level caching by URL), (3) authorization is more complex (field-level access control), (4) N+1 query risks require a DataLoader pattern, (5) most of our reads are well-defined resource fetches, not arbitrary graph queries. |
| **gRPC** | Excellent for inter-service communication. Rejected because browser clients require gRPC-Web (extra proxy), tooling for debugging is weaker, and the benefits (binary protocol, streaming) are unnecessary for our use case. |
| **tRPC** | End-to-end type safety between Next.js and the API. Rejected because our backend is Python (FastAPI), not TypeScript. tRPC requires a TypeScript server. |

**Why REST:**
- Universal — every HTTP client, every developer, every tool understands REST.
- Cacheable — HTTP caching semantics (ETags, Cache-Control) work out of the box.
- FastAPI generates OpenAPI specs automatically — free documentation and client generation.
- Simple authorization — endpoint-level permission checks map directly to resource operations.
- Debuggable — curl, Postman, browser DevTools all work without plugins.

**Trade-offs:**
- Over-fetching — some endpoints will return more data than the client needs. Mitigated by designing focused endpoints and using sparse fieldsets where needed.
- Multiple requests for related data — the frontend may need to fetch a memory and its graph edges separately. Mitigated by embedding related data in responses where the access pattern is predictable.

**Future Migration Path:** If GraphQL becomes justified (e.g., a public API for third-party integrations with diverse query needs), it can be added as an additional API layer on top of the same service layer. REST and GraphQL can coexist — GraphQL resolvers call the same services as REST handlers.
