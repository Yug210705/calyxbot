# ADR-011: UUIDs as Primary Keys

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use UUIDs (v4) as primary keys for all tables.

**Context:** Primary keys are used in URLs, API responses, log entries, and cross-table references. The choice of key format has implications for security, performance, and distributed systems compatibility.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Auto-increment integers** | Enumerable — an attacker can guess valid IDs by incrementing. Exposes business metrics (ID 10,000 implies ~10,000 records). |
| **ULIDs** | Sortable, lexicographically ordered. Attractive, but PostgreSQL has no native ULID type — requires a custom extension or string storage. Supabase defaults to UUID. |
| **CUIDs / NanoIDs** | Shorter than UUIDs, collision-resistant. Same issue — no native PostgreSQL type. String storage wastes index space. |

**Why UUIDs:**
- Non-enumerable — prevents IDOR attacks and business metric leakage.
- Native PostgreSQL type — 16 bytes, indexed efficiently, built-in generation via `gen_random_uuid()`.
- Supabase default — Auth user IDs are UUIDs. Using UUIDs everywhere avoids type mismatches.
- Distributed-safe — UUIDs can be generated by any client or service without coordination. Important for future service extraction.

**Trade-offs:**
- Larger than integers (16 bytes vs. 4/8 bytes). Increases index size and join cost. Negligible at MVP scale.
- Not naturally ordered — cursor-based pagination must use composite cursors `(created_at, id)` instead of `id` alone.
- Less human-readable in logs. Mitigated by always including contextual identifiers (org slug, document title) alongside UUIDs in log entries.

**Future Migration Path:** No migration anticipated. UUIDs are the industry standard for multi-tenant SaaS applications.
