# ADR-007: PostgreSQL for Graph Relationships over a Graph Database

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Model the memory graph using PostgreSQL tables (`entities`, `memory_edges`) rather than a dedicated graph database.

**Context:** The memory graph connects memories to people, projects, systems, clients, decisions, and each other. Graph traversal is core to answering questions like "who knows about X?" and "why was this decision made?" We need a graph-capable storage layer.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Neo4j** | Best-in-class graph database. Rejected because it adds a second database to operate, requires data synchronization with PostgreSQL, doubles the operational surface, and is overkill for MVP-scale graph sizes. |
| **Amazon Neptune** | Managed graph DB. Same objections as Neo4j, plus AWS vendor lock-in. |
| **Apache AGE (PostgreSQL extension)** | Adds Cypher query language to PostgreSQL. Promising, but less mature than pgvector. Community and production usage is still limited. |

**Why PostgreSQL:**
- No additional infrastructure — the graph lives in the same database as everything else.
- Transactional consistency — graph edges are created in the same transaction as the memory they connect. No sync lag.
- Adequate for MVP scale — organizations with thousands of memories and tens of thousands of edges are well within PostgreSQL's capability for 1–2 hop traversals.
- Familiar technology — the team doesn't need to learn Cypher or Gremlin to build the MVP.
- RLS applies — graph edges inherit the same tenant isolation as every other table.

**Trade-offs:**
- Multi-hop traversals (3+ hops) require recursive CTEs, which are less expressive and potentially slower than native graph queries.
- No native graph algorithms (shortest path, community detection, centrality) without application-level implementation.
- The polymorphic `source_node_type/target_node_type` pattern sacrifices foreign key constraints for flexibility.

**Future Migration Path:**
1. **First step:** Apache AGE extension — adds Cypher to PostgreSQL without infrastructure changes.
2. **Second step:** If AGE is insufficient, introduce a dedicated graph database as a materialized secondary index. PostgreSQL remains the source of truth; the graph DB is a query-optimized projection. The service layer queries through a `GraphRepository` interface — the swap is a repository implementation change.
