# ADR-004: PostgreSQL + pgvector for Storage and Vector Search

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Use PostgreSQL with the pgvector extension for both relational data and vector similarity search.

**Context:** Calyx stores structured relational data (organizations, users, memberships, memories, audit logs) and vector embeddings (for semantic search over memories). We could use a separate vector database for embeddings or consolidate into PostgreSQL.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Pinecone** | Purpose-built vector DB with excellent performance. Rejected because it adds a separate service to manage, a separate billing relationship, and requires syncing data between PostgreSQL and Pinecone. Operational complexity is too high for MVP. |
| **Weaviate** | Full-featured vector DB with hybrid search. Same objection as Pinecone — separate infrastructure. |
| **ChromaDB** | Lightweight, embeddable. Not production-grade for enterprise workloads. No managed hosting. |
| **PostgreSQL + pg_embedding** | Alternative PostgreSQL vector extension. Less mature than pgvector, smaller community. |

**Why PostgreSQL + pgvector:**
- Single database for all data — relational and vector. One connection pool, one backup strategy, one operational surface.
- ACID transactions — embedding inserts and memory creation happen in the same transaction. No eventual consistency between the relational and vector stores.
- org_id filtering — vector searches are scoped by organization in the same query. No need for external metadata filtering.
- HNSW indexing — pgvector supports HNSW indexes, which provide good recall and don't require retraining.
- Supabase includes pgvector — no additional setup or cost.

**Trade-offs:**
- pgvector is slower than purpose-built vector databases at large scale (millions of vectors). For MVP scale (tens of thousands of vectors per org), performance is more than adequate.
- HNSW index build time increases with vector count. Incremental inserts are handled well, but a full reindex is expensive.
- pgvector stores vectors in PostgreSQL heap pages, which increases database size and backup time.

**Future Migration Path:** If vector search becomes a performance bottleneck, the `embeddings` table has a clean interface. We can introduce a dedicated vector database as a secondary index:
1. Write embeddings to both PostgreSQL (source of truth) and the vector DB (search index).
2. Route search queries to the vector DB.
3. Keep PostgreSQL as the authority for embedding metadata and org-scoped filtering.

The service layer queries through a `SearchRepository` interface — swapping the implementation is a repository change.
