# ADR-016: Asyncpg as PostgreSQL Driver

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-07-01
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Standardize on `asyncpg` (via `postgresql+asyncpg://`) as the exclusive PostgreSQL database driver across the entire Python backend, for both FastAPI runtime execution and Alembic migrations.

**Context:** FastAPI is built for high-concurrency async workloads. Using synchronous database drivers like `psycopg2` can block the event loop, causing severe latency spikes under load. During Sprint 1, we encountered issues where our migrations (`env.py`) relied on `psycopg2` while the application code expected `asyncpg`. This divergence caused `ModuleNotFoundError` crashes during `alembic upgrade head`.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **psycopg2** | Synchronous driver. Blocks the ASGI event loop. Not suitable for a modern FastAPI application. |
| **psycopg (psycopg3)** | Excellent modern driver with async support. However, `asyncpg` historically benchmarks faster and is heavily battle-tested with SQLAlchemy's async extension. |
| **asyncpg for app, psycopg2 for migrations** | Leads to dual-driver dependencies, conflicting connection string formats (`postgresql://` vs `postgresql+asyncpg://`), and deployment edge cases. |

**Why asyncpg:**
- Maximum performance for asyncio-based Python applications.
- Seamless integration with `SQLAlchemy` async sessions (`AsyncSession`).
- Enforces consistency between the CI/CD migration runner environment and the production application environment.

**Trade-offs:**
- Adds complexity to Alembic, which traditionally expects synchronous drivers. We must use `context.configure(connection=connection)` with an async engine or ensure synchronous wrappers (`run_sync`) are properly managed in `env.py`.
- Slower initial connection pooling compared to native sync drivers, though negligible with connection poolers (PgBouncer/Supavisor).

**Future Migration Path:** If `psycopg3` becomes the definitive async standard for SQLAlchemy, migration requires simply updating the dependency and connection string scheme to `postgresql+psycopg://`.
