# ADR-017: RBAC Architecture (String-Based Granular Permissions)

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-07-01
**Owner:** Architecture Team

---

**Decision:** We will use granular, string-based permission identifiers (e.g., `organization.update`, `invitation.create`) instead of a composite `Resource` and `Action` model. Permissions will be resolved using an `AuthorizationContext` object.

**Context:** The initial RBAC design proposed separate `Resource` and `Action` columns, which led to implicit logic and complex matrix evaluations. We also needed to ensure the authorization logic remains decoupled from the specific user framework to support future features like Attribute-Based Access Control (ABAC).

**Implementation Details:**
- Permissions are strictly formatted strings: `resource.action` (e.g., `memory.delete`).
- `AuthorizationContext` encapsulates the User, Membership, Organization, and resolved Permissions.
- The `AuthorizationService` receives this context and strictly checks for the presence of the required string permission. Hardcoded role checks (e.g., `if role == 'admin'`) are forbidden in business logic.

**Why:**
- Simplifies permission caching and indexing.
- Provides fine-grained control and explicitly maps to API operations.
- Scales gracefully to handle complex scenarios like custom roles.

**Future Considerations:** If custom roles are introduced, they will simply map to a subset of these defined permission strings.
