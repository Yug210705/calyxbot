# ADR-019: Repository Pattern

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-07-01
**Owner:** Architecture Team

---

**Decision:** We will strictly enforce the Repository Pattern to abstract data persistence from the Service Layer. Services must never interact directly with SQLAlchemy models or sessions.

**Context:** Allowing business logic services to construct SQLAlchemy queries directly tightly couples the business layer to the database framework. This impedes unit testing (requiring actual databases rather than simple mocks) and makes future database migrations severely difficult.

**Implementation Details:**
- Repositories (e.g., `OrganizationRepository`, `MembershipRepository`) encapsulate all database access.
- Services define or rely on the Repository interfaces.
- Controllers/Routers parse requests, invoke Services, and return responses. They do not contain business logic.
- Pipeline: `Router -> Service -> Repository -> Database`.

**Why:**
- Ensures clean separation of concerns.
- Dramatically improves testability by allowing Repositories to be mocked.
- Prevents database implementation details from leaking into domain logic.

**Future Considerations:** Repositories can easily be wrapped in caching decorators without altering the underlying service logic.
