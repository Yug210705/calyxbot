# ADR-010: Contextual Permissions (RBAC + Scope Constraints)

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Supplement RBAC with contextual scope checks in the service layer. A permission grants the *capability*; the service layer enforces the *scope*.

**Context:** RBAC alone cannot express "Managers can edit documents, but only in workspaces they own." The RBAC table says the Manager role has `document:update`. The scope restriction requires checking workspace membership — a business rule, not a permission.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **Encode scope in permissions** (e.g., `document:update:own_workspace`) | Permission explosion. Every combination of action and scope becomes a separate permission. Unmanageable. |
| **Full ABAC** | Solves the problem elegantly but introduces policy language complexity. Premature for MVP. |
| **Ignore scope, grant full access per role** | Over-permissioning. A Manager shouldn't edit documents in workspaces they don't belong to. |

**Why Contextual Permissions:**
- RBAC answers "does this role have this capability?" — a fast, cacheable check.
- The service layer answers "does this user have the right scope for this specific resource?" — a business logic check that belongs in the service, not in the permission table.
- Clear separation — permissions are data; scope rules are code. Both are testable, but they're tested differently.
- Avoids permission explosion while maintaining precise access control.

**Trade-offs:**
- Scope logic is scattered across services — each service implements its own scope checks. Mitigated by extracting common scope checks into shared utilities (e.g., `is_workspace_member(user, workspace_id)`).
- Scope rules are in code, not in a policy engine. This means they're harder to configure without code changes. Acceptable for MVP; revisit if enterprise customers need admin-configurable scope rules.

**Future Migration Path:** If scope rules become complex, extract them into a lightweight policy engine (not a full ABAC system — a simple rules engine that evaluates `{role, action, resource_attributes}` tuples). The service layer calls the engine instead of inline checks.
