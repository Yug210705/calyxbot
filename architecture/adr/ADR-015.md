# ADR-015: Memory Health as a First-Class Product Metric

**Version:** 1.0
**Status:** Approved
**Last Updated:** 2026-06-30
**Owner:** Architecture Team
**Related Documents:**
- [Architecture Overview](../system/architecture-overview.md)

---

**Decision:** Memory Health — a composite organizational metric measuring knowledge coverage, freshness, verification, and bus factor — is a core product feature, not an analytics afterthought.

**Context:** Most knowledge management tools measure usage (page views, edits, search queries). These metrics tell you whether the tool is being used, not whether the organization's knowledge is healthy. Calyx's value proposition is preserving organizational memory — we must measure whether that's actually happening.

**Alternatives Considered:**

| Alternative | Reason Rejected |
|---|---|
| **No health metrics** | We can't tell customers whether our product is working. We can't identify at-risk knowledge before it's too late. |
| **Usage analytics only** (page views, DAU, search volume) | Measures tool adoption, not knowledge health. An organization with high usage but zero verification is at risk. |
| **Per-document metrics** (views, edits per document) | Too granular for executive decision-making. Doesn't reveal systemic issues (bus factor, coverage gaps). |

**Why Memory Health:**
- Proactive risk identification — bus factor analysis reveals single-person dependencies before the person leaves.
- Executive visibility — leadership can see organizational knowledge health at a glance, not just raw usage numbers.
- Actionable — the health dashboard produces specific recommendations ("Alice is the only person who has documented the billing service").
- Differentiator — no competitor provides organizational knowledge health scoring. This is unique to Calyx.
- Drives adoption — when managers see their team's health score, they're motivated to improve it. The metric creates a positive feedback loop.

**Trade-offs:**
- Gaming risk — visible scores can be gamed (creating low-quality memories to boost coverage). Mitigated by weighting quality (confidence) in the score formula, not just quantity.
- False precision — a composite score implies more precision than the underlying data supports. Mitigated by presenting scores as ranges/bands (Excellent / Good / At Risk / Critical), not exact numbers.
- Maintenance — the health calculation is a batch process that must be kept in sync with the memory model. Any schema change to memories must be reflected in the health calculation.

**Future Migration Path:** Health metrics will become more sophisticated with integration data (e.g., correlating GitHub commit velocity with documentation freshness). The health calculation is a read-only aggregation over the memory tables — it can be enhanced without changing the underlying data model.
